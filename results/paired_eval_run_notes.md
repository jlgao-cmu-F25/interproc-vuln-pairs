# Paired C evaluation run notes

- Deployment: the supplied Azure `gpt-4.1-mini-1` deployment, Responses API.
- Protocol: original CO/CC/CK prompts, temperature 0, maximum 4096 output tokens.
- Scheduling: 32 workers, at most 200,000 reserved tokens per rolling 60 seconds.
- Budget: $10 using reference token rates with a 25% margin. Successful usage,
  uncertain requests, and historical pilot attempts remain in the same ledger.
- Resume: atomic per-response checkpoints and a durable per-request cost ledger.
  Interruptions stop new calls and preserve responses already in flight.

## Pilot output-limit correction

The initial 400-token ceiling was too small for prompts that require a detailed
explanation before the `CLASSIFICATION` line. The first stopped checkpoint had
81 rows, 132 successful API responses, and $0.2581 of budget-accounted cost.
57 rows lacked a classification because their explanations were truncated.

The ceiling was restored to 4096, matching `repro/live_rerun.py` and the pinned
upstream `src/utilities/run_openai.py`. The truncated responses were retained
and tagged `superseded_by_output_limit`; those rows were reopened for the
normal classification/retry protocol. Complete, parsed pilot responses were
reused. All pilot costs still count toward the $10 cap. Reports must distinguish
the budget amount, which includes the margin, from the provider invoice.

The local fallback was stopped at the user's request; future paid requests
must run in Colab only. A local STOP flag remains in place. The
portable `notebooks/milestone_colab_ready.ipynb` bundles the current source and
uses a Google Drive checkpoint directory when run in Colab. No GitHub push is
required to use that notebook. `tools/make_notebook.py --with-checkpoint` also
creates `milestone_colab_resume.ipynb` with the existing responses and budget
ledger for import into Drive before Colab resumes paid requests. API keys and
the local STOP flag are excluded from the bundle.

## Colab setup hold

The notebook and the 263-row checkpoint have been uploaded through the Drive
connector. The checkpoint folder also contains `colab_control.json` (initial
action `hold`) and `colab_status.json` (initial phase `awaiting_setup`). The
Colab controller accepts a start only for its freshly published runtime ID;
the agent must first verify runtime configuration and can verify liveness with
a fresh ping nonce. No paid requests are authorized before Colab configuration
has completed. The controller supports a stop command during evaluation.

Important analysis caveats:

- The authors' published F1 is positive-only (precision=1 by construction),
  whereas the new paired F1 includes candidate-negative fixed code. Compare
  matched vulnerable recall separately; do not subtract the two F1 scores.
- 24 final labels retain parsed 400-token pilot attempts (CO:18, CC:1, CK:5).
  The remaining 1,412 final labels use 4,096. An exclusion sensitivity is saved.
- CVE-2017-5850 and CVE-2020-5208 each retain one unrecovered function inside
  fixed prompts. Excluding these CVEs barely changes the high fixed-alert
  rates, but negatives still need the uncompleted 30-pair manual review.
- `raw_cves` contains duplicate CVE records. `_load_raw()` uses filesystem
  enumeration order with last-record-wins. For three CVEs, eight fixed-prompt
  hashes in the local Windows-generated directory differ from the actual
  Colab hashes. The offline audit reconstructs all actual fixed hashes from
  candidate source records and freezes the matching filenames. All 718
  vulnerable prompts match the authors' originals. Do not regenerate paid
  prompts on another platform and silently assume input identity.
- Deployment identity is recorded as `gpt-4.1-mini-1`; an immutable model
  snapshot identical to the paper is not established. The 263 initial rows
  were migrated into Colab; they were not newly inferred there.
